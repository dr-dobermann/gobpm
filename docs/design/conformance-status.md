## 4. XML-interchange tier — the **server's** half of conformance

**Corrected 2026-08-02.** This section previously read *"Per BPMN §2.1.2,
Process Execution Conformance does not require XML import/interchange."*
That is wrong twice over. There is no §2.1.2 — Process Execution Conformance
is **§2.3** — and its second requirement says the opposite:

> **§2.3.2 Import of Process Diagrams** — "The tool claiming Process Execution
> Conformance type **MUST support import** of BPMN Process diagram types
> including its definitional Collaboration."

What makes this tier still absent from *this* tracker is not that it is
optional, but **whose obligation it is**. Both §2.3 requirements are addressed
to "the tool", and gobpm ships as a library plus, built on it, the
`gobpm-server` product ([SAD-001](SAD-001-vision-and-architecture.md) §2, §14).
§2.3.1 (execution semantics) is the library's target and is what this tracker
measures. **§2.3.2 is the server's**, delivered through the converter
(`pkg/convert/bpmn`, ADR-024 / the SRD-089 series), which covers the
executable element set — multi-process documents and the definitional
Collaboration included — so the import-side coverage is tracked with that
work (#335 holds what remains).

These elements therefore matter to the **server's** conformance claim, not the
library's:

`Definitions` (the registration layer plays the container role), `EndPoint`
(rides the ADR-004 remote transport), `Auditing`/`Monitoring` placeholders, the
vendor `Extension*` model types.

**`Lane`/`LaneSet` is NOT one of them** — it is a **library** gap, tracked at
[#261](https://github.com/dr-dobermann/gobpm/issues/261). Execution may ignore
lanes (§2.3.1, no token semantics), but the *model* must carry them: §2.3.2
obliges an importer to preserve a modeller's diagram, and ADR-024 §2.8's
semantic round-trip cannot re-export a structure the model never stored. The
type does not exist today, so a lane-bearing diagram cannot survive
import→export. Model-only, no execution wiring — the tracker's 🟡.
